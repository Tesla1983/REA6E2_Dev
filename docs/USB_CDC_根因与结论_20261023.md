# RA6E2 USB CDC 排障结论（2026-10-23）

> 目标：Type-C 直连 P814/P815 原生 USB，做成 CDC 虚拟串口。
> 起点症状：Windows 报 `VID_0000&PID_0002`「设备描述符请求失败 / 错误43」，
> 固件侧 `g_usb_events` 恒 0。

## 一、先纠正一个历史误判

上一轮把 `USBCKCR` 读在 `0x40047074`，据此认为"USB 时钟没配"。

**基址错了**：`R7FA6E2BB.h` 里 `R_SYSTEM_BASE = 0x4001E000`（`0x40047000` 不是 CGC）。

在正确基址实测：

| 寄存器 | 地址 | 实测值 | 含义 |
|---|---|---|---|
| `USBCKDIVCR` | `0x4001E06C` | `0x06` | = `BSP_PRV_UCK_DIV`，即 **/5** |
| `USBCKCR` | `0x4001E074` | 低字节 `0x05` | `USBCKSEL=5=PLL`，`USBCKSRDY=0`（已稳定） |
| `SCKSCR` | `0x4001E026` | `0x05` | 系统时钟 = PLL |
| `PLLCR` | `0x4001E02A` | `0x00` | PLL 运行中 |
| `SCKDIVCR` | `0x4001E020` | `0x31002332` | 各分频已设 |

⇒ **PLL 240 MHz ÷ 5 = 48 MHz，USB 时钟完全正常**。该假设作废。

## 二、根因 A：P407 是 RA6E2 唯一的 `USB_VBUS` 脚，被 I2C 占了

数据手册 QFN48 引脚表：

```
P407 = SDA0_B / SSIBCK0_A / USB_VBUS      （没有独立的 USBVBUS 专用脚）
```

工程 `configuration.xml` 里 `i3c_fslash_iic.sda0.p407` ⇒ **P407 固定为 IIC0-SDA0（1.3" OLED）**。

PFS 选中 IIC 后，USB 模块的 VBUS 输入被物理断开 ⇒ `INTSTS0.VBSTS` 恒 0
⇒ `DVSQ = USB_DS_SPD_DFLT`（Suspend Default）⇒ 控制器不完成控制传输 ⇒ 枚举失败。

**修复**：`USB_CDC_Init()` 里在 `R_USB_Open` 之前把 P407 切成 `USB_FS`：

```c
R_IOPORT_PinCfg(&g_ioport_ctrl, BSP_IO_PORT_04_PIN_07,
                IOPORT_CFG_PERIPHERAL_PIN | IOPORT_PERIPHERAL_USB_FS);
```

实测 **`g_usb_vbsts = 1`** ⇒ 板上 VBUS 确实接在 P407，只是此前被 I2C 复用切断。

## 三、根因 B（决定性）：裸机 FSP 必须自己派发 USB 事件

`r_usb_pinthandler_usbip0.c`，`BSP_CFG_RTOS == 0` 时 ISR 只做两件事：

```c
usb_pstd_interrupt_handler(&type, &status, ip);        /* 只"解码" */
g_usb_pstd_usb_int.buf[wp++] = {type, status, p_cfg};  /* 塞进环形缓冲 */
```

**它不调用 `usb_pstd_interrupt()` 去派发。** 派发在：

```c
/* r_usb_pdriver.c:989  usb_pstd_pcd_task() */
if (g_usb_pstd_usb_int.wp != g_usb_pstd_usb_int.rp) {
    usb_pstd_interrupt(buf[rp].type, buf[rp].status, buf[rp].p_cfg);
    rp++;
}
```

RTOS 模式下这是 PCD 任务的活；**裸机必须由应用反复调用 `usb_pstd_pcd_task()`**。
本工程从未调用过 ⇒ 所有 `VBINT/DVST/CTRT` 都堆在缓冲里烂掉。

典型表现（修复前实测）：

- ISR 确实进了 10 次，`INTSTS0` 累积出现过 `VBINT/RESM/SOFR/DVST/CTRT`
- SETUP 寄存器里躺着完整请求：`USBREQ=0x0680`(GET_DESCRIPTOR)、`VAL=0x0100`、`LENG=0x40`
- 但 `USBADDR=0`、`g_usb_pstd_data_cnt[pipe0]=0`、`CFIFOCTR=0` ⇒ 描述符永远发不出去

**修复**：在 ISR 包装里解码完**立刻就地排空**（主循环排空太慢会撑爆缓冲丢事件）：

```c
usbfs_interrupt_handler();
for (k = 0; k < 8; k++) { usb_pstd_pcd_task(); }
```

## 四、修复效果（实测）

| 项目 | 修复前 | 修复后 |
|---|---|---|
| `USBADDR` | 0 | **0x24 ~ 0x26**（SET_ADDRESS 成功） |
| `INTSTS0.DVSQ` | Suspend Default | **Configured (0x30)** |
| `g_usb_cfg_cnt` | 0 | **1** |
| `g_usb_events` | 0 | 7 ~ 11 |
| Windows | `VID_0000&PID_0002` 错误43 | **`USB\VID_045B&PID_0263`「USB 串行设备 (COM15)」，usbser，CM_PROB_NONE** |

## 五、根因 C：CDC 类请求必须由应用自己应答

FSP 的 `usb_peri_class_request_rwds()` 在 PCDC-only 工程里**不代发数据**，只做：

```c
ctrl.setup = *req; ctrl.data_size = 0; ctrl.status = USB_SETUP_STATUS_ACK;
ctrl.type = USB_CLASS_REQUEST;
usb_set_event(USB_STATUS_REQUEST, &ctrl);   /* 转交应用 */
```

原 `usb_callback` 里 `USB_STATUS_REQUEST` 落进 `default: break;` ⇒ 主机
`GET_LINE_CODING` 永远收不到回复 ⇒ 端口即使建出来也打不开。

补法（`usb_callback`）：

| 请求 | 处理 |
|---|---|
| `0x21 GET_LINE_CODING` | `R_USB_PeriControlDataGet(&g_basic0_ctrl, s_line_coding, 7)` |
| `0x20 SET_LINE_CODING` | `R_USB_PeriControlDataSet(&g_basic0_ctrl, s_line_coding, 7)` |
| `0x22 SET_CONTROL_LINE_STATE` / `0x23` | **什么都不做**（FSP 的 `wnss()` 已自动 `ctrl_end`） |

⚠ 必须用 `R_USB_PeriControlDataGet/Set`（走 pipe0 控制管道）；
`R_USB_Write/Read(dst=USB_PCDC)` 走的是**批量管道**，对控制请求无效。

## 六、根因 D：`BEMPENB.pipe0` 没开 —— 控制传输收不了尾

实测证据（决定性）：

- `BEMPSTS = 0x0001` ⇒ 主机**已经把 7 字节读走**（数据确实发出去了）
- 但 `BEMPENB = 0x0020` ⇒ **pipe0 的 BEMP 中断没使能** ⇒ `INTSTS0.BEMP` 不置位
  ⇒ FSP 收不到"缓冲区已空" ⇒ 控制传输不收尾 ⇒ 状态阶段不产生
- 现象链：`g_usb_req_done_cnt = 0`、`data_cnt[pipe0]` 卡在 7、pipe0 一直忙
  ⇒ 后续 `SET_LINE_CODING` / `SET_CONTROL_LINE_STATE` 全超时
  ⇒ `SerialPort.Open` 报 `OSError(121, '信号灯超时时间已到')`

原因：设备模式下 `usb_ctrl_read()` 走的是 `usb_pstd_ctrl_write()`
（`r_usb_cdataio.c:373`），后者只开了 `BRDYENB(pipe0)`，**漏了 `BEMPENB(pipe0)`**。

修法（1 行）：

```c
R_USB_FS0->BEMPENB |= (uint16_t) 0x0001u;   /* pipe0 BEMP 使能 */
```

实测：`g_usb_req_done_cnt` 由 0 变 1，控制传输正常收尾。

## 七、根因 E：`usb_pstd_pcd_task()` 的位置

- **不能放 ISR**：FSP 明确写 `R_USB_PeriControlDataGet/Set` 禁止在中断/回调里调用
  （`r_usb_basic.c:3670`）。
- **也不能一秒才调一次**：主循环原有 `4 × R_BSP_SoftwareDelay(250ms)` = 1 s/圈，
  而 `USB_INT_BUFSIZE` 只有 **8** ⇒ 枚举突发事件溢出丢事件（有时卡在 Address 态）。

最终方案：新增 `USB_CDC_Poll()`，主循环那 1 秒拆成 `500 × 2ms`，每片都排空。

## 八、最终结果（全部实测）

| 项 | 结果 |
|---|---|
| `USBADDR` | 0x2A~0x2C |
| `INTSTS0.DVSQ` | **Configured** |
| `g_usb_cfg_cnt` | 1 |
| `g_usb_req_cnt / req_done` | 2 / **1**（控制传输正常收尾） |
| Windows | `USB\VID_045B&PID_0263`「USB 串行设备 (**COM15**)」，usbser，CM_PROB_NONE |
| `SERIALCOMM` | `\Device\USBSER003 : COM15` |
| `SerialPort.Open('COM15')` | **OPEN OK** |
| 主机写 5 字节 | `g_usb_rx_bytes = 5`、`g_link_rx_bytes = 5` |

⇒ **USB CDC 虚拟串口端到端可用**。

⚠ 注意：`COM15` 在枚举完成后约数十秒才会出现在 `GetPortNames()`；
刚复位时短暂不可见属正常，不要当成失败。

## 九、当前固件里的诊断脚手架（收尾时可清理）

- `src/usb/usb_isr_probe.c` + `ra_gen/vector_data.c` 的 `[0] = usbfs_isr_probe`：
  纯诊断（数 ISR 次数、记事件序列）。**ISR 里已不再做派发**，删掉不影响功能。
  备份：`.workbuddy/backup/vector_data.c.20261023`
- `usbfs_isr_probe()` 里的 CTRT 120-NOP 延迟：已证明 PRE/POST 的 `INTSTS0` 完全一致，**可删**。
- `USB_CDC_SETUP_KICK`：默认已置 0，**可删**。
- 诊断用全局：`g_usb_req_cnt / g_usb_req_done_cnt / g_usb_req_last /
  g_usb_get_err / g_usb_stat_err / g_usb_cfifo_after / g_usb_pipe0_after /
  g_usb_dcnt_after` —— 建议保留 `req_cnt/req_done`，其余可删。
- ⚠ **不能删的两个功能性补丁**：`R_USB_FS0->BEMPENB |= 0x0001` 与 `USB_CDC_Poll()`
  的 2 ms 主循环调用。

## 十、根因 F：open / close 各卡 30 s —— usbser 在等 DTR 相关的控制传输收尾

### 现象

数据通路全通，但每次打开/关闭 COM15 都要整整 **30.0 s**。

### 定位：把 pyserial 拆成 Win32 API 逐个计时（`host/usb_cdc_timing.py`）

| 步骤 | 耗时 |
|---|---|
| `CreateFileW` | 0.00 s |
| `EscapeCommFunction(SETDTR)` | **30.01 s** |
| `EscapeCommFunction(SETRTS)` | 0.00 s |
| `EscapeCommFunction(CLRDTR)` | **30.01 s** |
| `EscapeCommFunction(CLRRTS)` | 0.00 s |
| `WriteFile` | 0.00 s |
| `CloseHandle` | **30.00 s** |

⇒ **只有 DTR 变化会卡**。usbser.sys 在 DTR 变化时同步等
`SET_CONTROL_LINE_STATE`（0x22）的**状态阶段(ACK)**，等不到就干等 30 s 再继续。

### 设备侧其实响应是即时的

固件里加了事件时间线（`g_usb_ss_hist_*`，tick ≈ 2 ms）。实测：

```
收到 0x22(wValue=2) → +1 tick 发通知 → +1 tick 写完成
```

设备在**请求到达后 1~2 个 tick** 就处理完了，主机却还在卡 30 s
⇒ **不是设备慢，是主机没收到"这次控制传输收尾了"的信号。**

### ⛔ 中途被证伪的假设（记录下来，别再走回头路）

1. **"host 在等 CDC 的 SERIAL_STATE 通知"** —— 通知确实发出去了
   （`g_usb_ss_sent=12`、`g_usb_ss_err=0`、写完成回调也回来了），
   但把位图**固定成 DSR=1**、甚至打开**持续模式每 50 ms 主动发一次**，
   30 s 依然不变 ⇒ **通知内容/时机都不是原因**。
2. **"wValue 的 DTR 位判断反了"** —— 确实反了（见下），但改对也没用。
3. **"配置描述符里端点重复"** —— FS 描述符是干净的，重复端点只在未被使用的 HS 数组里。

### ✅ 发现 1：usbser 的 wValue 位定义与 CDC 规范文字**相反**

单操作隔离实验（`--minimal`，只做 CreateFileW + SETDTR + CloseHandle）：

| 主机操作 | 设备侧收到的 wValue |
|---|---|
| SETDTR | **0x0002** |
| CloseHandle | 0x0000 |

完整一轮的 wValue 序列 = **0, 2, 3, 2, 0** ⇒ **bit1 = DTR、bit0 = RTS**
（CDC 规范 PSTN1200 写的是 bit0=DTR、bit1=RTS，**实测相反**）。
⇒ 固件里原来用 `wval & 0x0001` 判 DTR 是错的，已改为 `g_usb_dtr_bit`（默认 0x0002）。

### ⛔ 发现 2（**已于 2026-10-24 证伪，别再引用**）：pipe0 的 `BEMPENB` 在 0x22 路径上没开

> **更正（2026-10-24）**：这个补丁已经在板上运行，`open` **依旧整整 30.05 s**，一点没变
> ⇒ 假设不成立。新的反证：`g_usb_req_cnt=11 / g_usb_req_done=9` —— 有数据阶段的类请求
> 都走到了 `USB_STATUS_REQUEST_COMPLETE`，说明**控制传输是完成的**，
> 不是"状态阶段(ACK)发不出去"。**30 s 的真实来源仍未定位**，见第十三节。

FSP 的 `usb_ctrl_read()` 走 `usb_pstd_ctrl_write()`，只开 `BRDYENB(pipe0)`，
**漏开 `BEMPENB(pipe0)`** ⇒ 主机把数据读走后 BEMPSTS 置位但 `INTSTS0.BEMP` 不置位
⇒ FSP 收不到"缓冲区已空" ⇒ 控制传输不收尾 ⇒ 主机等 30 s。

我们之前**只在 `0x21 GET_LINE_CODING` / `0x20 SET_LINE_CODING` 分支**补了
`BEMPENB |= 0x0001`，**0x22 SET_CONTROL_LINE_STATE 漏了** ⇒ 它的状态阶段发不出去。

**修法**：在 `USB_STATUS_REQUEST` 分支入口处**无条件**打开 pipe0 的两个中断
（`BRDYENB |= 1` / `BEMPENB |= 1`），对所有类请求生效。

> ⚠ **状态：已编译（47,492 B）→ 已烧进板子（2026-10-23，`Finished in 36.93s`，
> `fw_tag = 0x4E54000C` = v12，`g_usb_ss_tick` 在涨 ⇒ 内核在跑）→ 验收未完成。**
> 也就是说 **这个假设还没有被证实**，引用时不要说"已修好"。见第十一节「待验收」。

### 附：DAPLink 烧录的纪律

今天这块 DAPLink 一烧就把自己卡死（一次 SWD 超时 ⇒ HID 命令引擎死 ⇒ 只能人工断电 30 s）。
规律：**探针刚断电复活后立刻烧，中间不要插别的 SWD 事务**；
唯一验证过能成的配方是 `--speed 400 --no-dblbuf`。
`scripts/flash_auto.py` 会守着等探针复活 → reset 目标 → 立刻烧。

⚠ 另外注意：`flash.sh` 原先**不认** `--connect-under-reset`（现在已支持），
导致 `flash_auto.py` 有一轮**空转 25 分钟没真烧**。而且这块板 **nRESET 没接线**，
所以 `--connect-under-reset` **在当前硬件上无效**。

## 十一、30 s 卡点的验收结果（2026-10-24 已验收：**未修好**）

**板上固件是好的**（v12、内核在跑），但**USB 没有枚举**（`g_usb_cfg_cnt = 0`）。

原因很明确，不是固件问题：

| 时刻 | 事件 | 结果 |
|---|---|---|
| 烧录成功 | `Finished in 36.93s` | **COM15 存在** ✅ |
| 随后一条 | `probe-rs reset --chip R7FA6E2BB --probe 0d28:0204` | **COM15 消失**，`g_usb_cfg_cnt` → 0 ❌ |

### 结论（2026-10-24 更新）：30 s **没有修好**，pipe0 假设作废

- 补丁在板上运行，`open` 依旧 **30.05 s**。
- 新反证：`g_usb_req_cnt=11 / g_usb_req_done=9` ⇒ 控制传输是完成的。
- 但**接收断流的 bug 是另一个问题**，已在第十三节定位并修好（这才是"数据不上屏"的原因）。
- 30 s 的真实来源**仍未定位**，从头查时请注意已知边界：
  只在 DTR 变化时卡、`SETRTS`/`CLRRTS` 瞬时返回、`CloseHandle` 也卡 30 s、
  设备侧 1~2 tick 就处理完、SERIAL_STATE 通知已排除。

### ⚠⚠ 铁律：这个项目上**不要用 `probe-rs reset`**

烧完要让程序跑起来，用**物理拔插 Type-C**；需要连 SWD 时再上 DAPLink。
（2026-10-24 补充：`probe-rs reset` 后设备**确实会重新枚举**，`cfg_cnt` 会变 1，
但 `SERIALCOMM` 里要过约 45 s 才出现 COM15，期间 open 可能报 `SetCommState` 错误 31。
所以拔插仍是最干净的方式。）


## 十二、硬件取舍：I2C 迁到 P408(SCL) + P206(SDA)

P407 只能是 I2C 或 USB_VBUS 二选一（同一根脚，硬件决定，软件绕不过）。

**开发板没有引出 P410/P411**（板上只引出 31 个脚），所以改用：

| 引脚 | 复用 | 用途 |
|---|---|---|
| `P408` | `SCL0_B` | I2C SCL（**不动**） |
| `P206` | `SDA0_C` | I2C SDA（**由 P407 迁来**，板子丝印也标 `SDA0`） |
| `P407` | `SDA0_B / USB_VBUS` | 专供 USB VBUS 检测 |

⇒ **硬件只改一根线**：OLED 的 SDA 从 P407 挪到 P206，SCL 保持 P408。

寄存器实测（PFS 基址 `0x40080800`）：

| 引脚 | 地址 | PFS | 含义 |
|---|---|---|---|
| P206 | `0x40080898` | `0x07010000` | PSEL=0x07 → IIC ✓ |
| P408 | `0x40080920` | `0x07010002` | PSEL=0x07 → IIC ✓ |
| P407 | `0x4008091C` | `0x13010002` | PSEL=0x13 → USB_FS ✓ |

顺带修掉一个真 bug：`bsp_i2c.c` 里把 SCL/SDA 写反了（写成 P407=SCL、P408=SDA，
实际是 P407=SDA0_B、P408=SCL0_B），导致总线恢复序列一直拉错脚。

## 十三、根因 G：插上 Type-C 但数据不上屏 —— 接收只进第一包就断流（2026-10-24 已修复）

### 现象
板子插上 Type-C，Windows 有 COM15，USB 已枚举；上位机按协议持续发帧，
但 3.5" 屏上 4 行布局正常、**全是 `--`**。

用 `tools/screen_shot.py` dump `g_u8g2_fb` 确认：**屏幕渲染完全正常**，只是没有数据。
所以问题不在屏、不在协议、不在显示代码，而在**数据根本没进 MCU**。

### 定位

设备侧计数器（探针读 RAM）：

| 量 | 值 | 判读 |
|---|---|---|
| `g_usb_cfg_cnt` | 1 | 已 Configured |
| `g_usb_vbsts` / `g_usb_dprpu` | 1 / 1 | VBUS 检测、D+ 上拉正常 |
| `BRDYENB`（`0x40090036`）| `0x0020` | pipe5 收包中断**已开** |
| `g_usb_rx_bytes` | **0** | 一个字节都没收到 |

绕过业务代码，直接用 pyserial 往 COM15 写 3 帧裸帧做隔离实验：

```
open 耗时 30.05 s
write #1  → 返回 50 B        ✅
write #2  → SerialTimeoutException  ❌
```

设备侧随即读到 `g_usb_rx_bytes = 0x32 = 50`、`g_link_frames = 1`
⇒ **只收到第一包，之后彻底断流。**

### 根因：`usb_read_arm()` 在中断/回调上下文里调用

原来在 `usb_callback()` 里这样写：

```c
case USB_STATUS_CONFIGURED:     ... usb_read_arm(); break;
case USB_STATUS_READ_COMPLETE:  ... usb_read_arm(); break;
```

而 `usb_read_arm()` 内部是 `R_USB_Read(...)`。**FSP 明令禁止在中断/回调里发起传输**
（与 `R_USB_PeriControlDataGet/Set` 同一条禁令）。

危险之处在于**它不报错，只是静默失败**：

1. 枚举完成时在回调里挂第一次 —— 碰巧成功；
2. 收完第一包在回调里重挂 —— **失败**；
3. ⇒ pipe5 再也不 armed ⇒ 主机后续 `WriteFile` 全部被 NAK ⇒ 2 s 写超时；
4. ⇒ 设备只收到第一包，屏上永远 `--`。

### 修法

回调里**只置标志**，真正的 `R_USB_Read` 放到主循环：

```c
static volatile bool s_rx_need_arm = false;

/* 回调里 */
case USB_STATUS_CONFIGURED:     s_configured = true;  s_rx_need_arm = true; break;
case USB_STATUS_READ_COMPLETE:  UART_Link_PushBytes(s_rx_buf, n); s_rx_need_arm = true; break;

/* USB_CDC_Poll()：排完 usb_pstd_pcd_task() 之后 */
if (s_rx_need_arm && s_configured) { s_rx_need_arm = false; usb_read_arm(); }
```

新增诊断量：`g_usb_read_err`（`R_USB_Read` 返回码）、`g_usb_read_arm_cnt`（累计挂起次数）。

### 可推广的教训

> **凡是「发起传输」的 API（`R_USB_Read` / `R_USB_Write` /
> `R_USB_PeriControlDataGet` / `R_USB_PeriControlDataSet`），
> 一律只在主循环调用；回调里只允许改标志位和计数器。**
> 违反后不是编译错误、不是运行错误，而是**静默不生效**——排查成本极高。

### 顺带确认的两件事

1. `open` 仍卡 **30.05 s**（`SETDTR`），但**不影响数据收发**（开完口之后写通了）。
2. 固件版本号 `g_nt_fw_tag` 仍是 **v12 = `0x4E54000C`**，本次改动没有升版
   ⇒ **当前 v12 有两个变体**，下次重烧时请顺手升到 v13。
